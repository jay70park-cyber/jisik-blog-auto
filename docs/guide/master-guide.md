# Part A — 콘텐츠 전략

## A1. 블로그 포지셔닝

> **지식산업센터 전문 + 그 생태계의 공장·상가**

지산을 주력으로 하되, **지산이 있는 지역의 공장과 상가**까지 다룬다.
상가·공장은 별개 분야가 아니라 지산 생태계의 일부로 접근한다.

**두 개의 사업 축**이 있고, 콘텐츠도 그에 맞춘다.

| 축 | 대상 | 콘텐츠 |
| --- | --- | --- |
| 중개업 (3년 뒤) | 일반 매매·임대 고객 | 지산 본류, 실거래 분석 |
| 컨설팅 (구상 중) | 경매로 취득하려는 사업자 | 경매 낙찰 분석 |

3년 뒤 사업 홈페이지 전환을 전제로, 방문자 구성이
**"사업·투자 목적으로 온 사람"** 중심이 되도록 관리한다.

### 요일 판별 주의

GitHub 러너는 **UTC**로 돈다. 한국 월요일 08:00은 UTC 일요일 23:00이라
`datetime.date.today()`를 그대로 쓰면 요일이 하루 어긋난다.
`pick_track()`은 반드시 KST로 변환해서 판단한다.

```python
kst = datetime.timezone(datetime.timedelta(hours=9))
today = datetime.datetime.now(kst).date()
```

## A3. 콘텐츠 설계 원칙 — 글 하나 = 판단 도구 하나

### 독자는 매 글마다 한 명만

| 독자 | 핵심 질문 |
| --- | --- |
| 임대수익 목적 투자자 | 이 조건에서 수익이 나는가 |
| 실사용 매수자 | 사는 게 나은가 빌리는 게 나은가 |
| 실사용 임차인 | 이 호실이 우리 업종에 맞는가 |

**독자에 따라 넘기는 데이터가 달라진다.**
우리 실거래 데이터는 매매뿐이라 임차인 글에는 재료가 되지 못한다.

```python
if "임차" in reader and category not in ("realprice", "auction"):
    realprice = ""          # 임차인 글에는 매매 데이터를 넘기지 않는다
```

단, 실거래·경매 트랙은 데이터가 주인공이므로 독자와 무관하게 항상 넘긴다.

④ 위험 신호 목록 / ⑤ 순서 안내

### 계산 예시를 만들지 않는다 — 2026-09-21 뒤집음

예전에는 독자 유형별로 계산 예시를 **만들라고 시켰다.**

```
임대수익 투자자 → 전용 30평, 분양가 3.5억, 보증금 3천/월 150만,
                  대출 60% 금리 5% 가정 시 실투자금 OO, 연수익률 OO%
```

그 결과 모델이 금리·월세·보증금을 지어내 5년 비용을 계산하고,
그 위에 **"매수가 임차보다 6,500만원 더 든다"** 같은 결론까지 세웠다.
숫자는 그럴듯했지만 전부 가정값이었고 독자 조건과 아무 관계가 없었다.

```
- 가정한 숫자로 계산 예시를 만들지 말 것
- 계산은 주어진 데이터(실거래·경매 집계)에 실제로 있는 숫자로만
- 계산 '방법'은 알려줘도 좋다 ("평당가 = 거래금액 ÷ 건물면적 ÷ 3.3058")
  공식과 확인 순서는 쓰되, 가정값을 대입한 결과는 쓰지 말 것
- 독자가 자기 숫자를 넣어야 하는 계산은 계산기 링크 한 줄로 넘길 것
```

**"내 경우 계산해보기" 섹션도 없앴다.** 섹션을 두면 채워야 할 칸이 생기고,
채우려면 숫자를 지어내게 된다. 지금은 관련 섹션 끝에 링크 한 줄만 붙인다.

계산기 탭은 본문 계산 내용과 맞아야 하고, **이 글의 산출물 유형과도**
맞아야 한다. 거래량을 읽는 글에 임대수익률 계산기를 붙이면 글 끝에서
화제가 갈린다. **맞는 탭이 없으면 계산기를 넣지 않는다.**
계산기는 채워야 하는 칸이 아니다.

### 판단 기준 3가지 — 정책 변경됨 (2026-08-19)

| 구분 | 판정 |
| --- | --- |
| "수익률 4% 이상이면 매수" | **금지** — 단정적 투자 권유, 책임 소재 |
| "전용률 50% 미만이면 실사용에 부적합" | **허용** — 사실 기반 확인 기준 |

**반영 위치 3곳** — 한 곳만 고치면 반쪽이 된다.
`generate_plan.py` / `generate_draft.py` / `content_rules.py`

> 기획 단계에서 정성적 기준만 만들어버리면, 본문 단계에서 아무리
> 사실 기반 기준을 요구해도 **재료 자체가 없다.**

### 기획 이력 — 같은 글이 반복되지 않게

`state/plan_history.json`에 최근 8회 기획(독자·산출물·판단기준)을 남기고,
다음 기획 프롬프트에 넣어 겹치지 않게 한다.

이력이 없던 때는 매번 "실사용 매수자 + ② 합격기준 + 전용률·업종제한"이
반복됐다. 키워드만 바뀌고 기획은 복사본이었다.

## A3-2. 판단 기준 규칙 — 2026-10-01 신설

### 규칙이 함정을 가르치고 있었다

2026-10-01 실거래 기획안에 이런 판단 기준이 나왔다.

```
매물 등록 건수가 최근 6개월 평균 실거래 건수의 3배를 넘는지 확인한다
등기부등본상 3년 미만 보유 매도 비중이 절반을 넘는지 확인한다
```

세 군데가 잘못됐다.

| 문제 | 왜 |
| --- | --- |
| **3배의 출처가 없다** | 지어낸 기준선이다. 독자가 믿을 이유가 없다 |
| **단위가 안 맞는다** | 매물 건수는 지금 쌓인 양(저량), 거래 건수는 기간당 흐르는 양(유량). 그대로 나눌 수 없다 |
| **독자가 할 수 없다** | 국토부 실거래가에는 **매도인도 호실도 안 나온다.** 등기부를 수십 건 떼야 비중이 나온다 |

원인은 모델이 아니었다. `content_rules.py`가 판단 기준의 **예시로**
이렇게 적고 있었다.

```
(예: "전용률 50% 미만 -> 실사용 부적합", "역까지 도보 10분 초과 -> 임차 수요 약함")
```

50%도 10분도 출처가 없다. **규칙이 직접 임의 기준선 만들기를 시범 보이고
있었으니 모델은 그걸 따랐을 뿐이다.** 09-21 에 계산 예시 자리에서 같은
실수를 찾아 고쳤는데, 판단 기준 자리에는 그대로 남아 있었다.

더 나쁜 것은 1차 관문이었다. `generate_plan.py`는 같은 예시를
**"좋습니다"** 라는 권장형으로 들고 있었다.

```python
- 다만 "전용률 50% 미만이면 실사용에 부적합" 같은 사실 기반의 확인 기준은 좋습니다.
```

### 지금의 규칙

`content_rules.py`의 `CRITERIA_RULES` 한 곳에 있다.

```
- 기준선을 지어내지 말 것. 숫자로 선을 긋되 출처가 없으면 쓰지 말 것
- 기준선을 쓰려면 둘 중 하나
  · 법령·고시·공공기관 기준에서 온 수치 — 출처를 함께 적을 것
  · 주어진 데이터에서 직접 계산해 낸 수치 — 계산 방법을 적을 것
- 출처 있는 선이 없으면 절대 기준 대신 상대 비교로
  "3배를 넘는지" 대신 "직전 같은 기간과 비교해 늘었는지"
- 단위가 다른 값을 배수로 비교하지 말 것
  비교하려면 "매물 수 ÷ 월 거래건수 = 소진에 몇 개월"처럼 단위를 맞출 것
- 독자가 그 자리에서 확인할 수 없는 항목은 기준으로 쓰지 말 것
  국토부 실거래가에 매도인도 호실도 없다는 것을 기억할 것
- 표본이 적은 항목에는 판단 보류를 함께 적을 것
  동탄 지식산업센터는 단지 하나에 분기 몇 건이다
- 확인 경로(사이트 → 메뉴 → 무엇을 고를지)를 함께 적을 것
```

### 세 관문이 같은 규칙을 쓴다

판단 기준은 기획에서 정해진다. **1차 관문을 막지 않으면 나머지는
뒤처리일 뿐이다.** 그래서 규칙을 상수로 떼어 세 곳이 공유한다.

```
content_rules.CRITERIA_RULES
   ├── generate_plan.py   기획 — cr.build_criteria_rules()
   ├── generate_draft.py  초안 — CONTENT_RULES 안에 포함
   └── verify_draft.py    검증 — 11번 '판단 기준의 타당성'
```

초안 단계도 바꿨다. 예전에는 기획의 판단 기준을 **"그대로 사용하되"**
살만 붙이게 했다. 기획에 나쁜 기준이 들어오면 검증 없이 통과했다.
지금은 **먼저 점검하고** 세 종류(출처 없는 기준선 / 확인 불가 /
단위 불일치)에 걸리는 항목을 갈아끼운다.

**교훈: 프롬프트에 예시를 적을 때는 그 예시가 곧 지시다.**
금지하려는 것을 예시로 들면 그것을 가르치는 셈이 된다.
지워야 할 예시를 "예전엔 이랬다"는 설명으로 남겨도 마찬가지다
(실제로 그렇게 고쳤다가 자체 검사에 걸렸다). 기록은 코드 주석에,
지시는 프롬프트에 — 섞지 않는다.

## A4. 트랙별 글 구조

트랙마다 글의 성격이 다르다. 실거래·경매는 **판단 도구가 아니라 현황 파악** 글이라
"무슨 일이 있었나 → 판단 도구 → 판단 기준" 흐름이 맞지 않는다.

구현 위치: `generate_draft.py`의 `structure_block`
(`if category == "auction"` / `elif "realprice"` / `else`)

### 지산 본류·지역 이슈 (기본 10단계)

```
1. 제목
2. ## 3초 요약            결론 한 문장 + 필요한 사람/필요 없는 사람
3. ## 무슨 일이 있었나
4. ## [산출물 유형에 맞는 도구]
5. ## 판단 기준 3가지      ← 기획의 기준을 점검하고 못 쓰는 것은 갈아끼운다
6. ## 동탄은 어떤가
7. ## 이 판단이 틀릴 수 있는 경우
8. ## 더 읽어보기
9. ## 이 주제를 고른 이유
```

**"내 경우 계산해보기"가 빠졌다 (2026-09-21).** 별도 섹션을 두면
채워야 할 칸이 생기고, 채우려면 숫자를 지어내게 된다.
지금은 관련 섹션 끝에 계산기 링크 한 줄만 붙인다. 상세는 A3.

### 실거래가 분석 (9단계)

```
1. 제목                          핵심 숫자가 드러나게
2. ## 3초 요약
3. ## 이번 집계 숫자              우리 데이터만. 외부 시세 사이트 금지
4. ## 눈에 띄는 것                특이값 2~3개와 그 이유
5. ## 이 숫자를 읽을 때 주의할 점  ★ 표본 쏠림·건물면적 기준 명시 (필수)
6. ## 내 물건은 어디쯤인가        → 계산기 링크
7. ## 직접 확인하는 법            실거래가 공개시스템 조회 순서
8. ## 더 읽어보기
9. ## 이 데이터에 대하여
```

### 경매 취득 (10단계)

```
1. 제목
2. ## 3초 요약
3. ## 이번 집계 숫자              지역별 매각가율·평당매각가
4. ## 유찰이 쌓이면 값은 얼마나 내려가는가   ★ 이 트랙의 핵심
5. ## 실거래가와 견주면            ★ 경매 평당가 vs 실거래 평당가
6. ## 이 숫자를 읽을 때 주의할 점  (필수)
7. ## 내가 보는 물건은 어디쯤인가  → 계산기 링크
8. ## 직접 확인하는 법            법원경매정보 조회 순서
9. ## 더 읽어보기
10. ## 이 데이터에 대하여
```

**5번이 이 트랙의 가장 큰 가치다.** 낙찰가율만 다루면 남들과 같지만,
우리 실거래 데이터와 나란히 놓으면 다른 데선 못 하는 분석이 된다.

### 시의회 회의록 특집 (9단계) — 2026-09-28 전면 재편

```
1. 제목
2. ## 3초 요약
3. ## 이건 무슨 회의인가        ★ 배경·용어 풀이·안건 표
4. ## 의원이 묻고, 집행부가 답한 것   ★ 질의 주체와 답변 부서
5. ## 사업별로 지금 어디까지 왔나
6. ## 회의는 어떻게 끝났나      ★ 가결·부결·시정요구사항
7. ## 다음에 지켜볼 것
8. ## 회의록 직접 보는 법
9. ## 이 주제를 고른 이유
```

**왜 바꿨나.** 09-24 초안의 제목이 "화성시 예산결산, 여윳돈 8천억인데
빚 1500억" 이었다. 이 글을 처음 읽는 사람은 배경 지식이 거의 없는데
갑자기 결론부터 나온다. 예산 결산이 무엇인지, 왜 이런 회의를 하는지,
주요 안건이 뭐였고 어떤 입장차가 있었고 결론이 어떻게 났는지 —
**회의록의 기본 취지**가 빠져 있었다.

3·4·6번이 그 자리를 채운다. 3번은 배경과 용어(순세계잉여금, 불용액,
계속비)를, 4번은 "누가 묻고 어느 부서가 어떻게 답했나"를,
6번은 회의가 어떻게 끝났는지를 담는다.

**논평으로 읽히는 문제도 여기서 풀렸다.** 원인은 정치적 평가가 아니라
문장 구조였다.

| 논평처럼 읽히는 쓰기 | 고친 쓰기 |
| --- | --- |
| 항목을 단정 문장으로 시작 | "~묻는 질의에, 집행부는 ~답했다" |
| "예산**만** 확보해둔" | 조사 하나가 판단이 된다. 뺀다 |
| 제목을 "A인데 B" 모순 형태로 | 사실 서술로 |

**재료가 없으면 지시도 소용없다.** 09-24 초안에 의결 결과가 안 들어간
것은 모델 탓이 아니라 회의록 요약에 그 정보가 없었기 때문이다.
B5 의 요약 범위 확대가 함께 가야 이 구조가 작동한다.

### A5-2. 금지 표현

- `~할 수 있습니다`, `~에 영향을 줍니다`, `~가 중요합니다` 같은
  조건부·당위 서술로 문단을 끝내지 말 것.
  **반드시 구체적 숫자나 확인 방법으로 끝낼 것**
- `전문가와 상담하세요`, `꼼꼼히 따져보세요`, `신중한 접근이 필요합니다` 금지
- 근거 없는 별점(★)·추천도 표 금지 → 조건별 판단 기준 표로 대체
- `문의 주세요`, `상담 환영`, 특정 매물 추천, 글 말미 상담 유도 금지

### A5-3. 숫자 의무

- 웹 검색으로 확인 가능한 수치는 구체적으로 넣되, **검색은 3회 이내로 제한**
- 실제 금액을 넣은 계산 예시 최소 1개 (독자 유형에 맞는 것으로)
- 모든 수치에 기준 시점과 출처
- 확인 안 된 수치는 `<mark>[평당 분양가 확인 필요]</mark>` 자리표시자로 남길 것
- 자리표시자는 문장 중간에 끼워 넣지 말고 문장을 끝낸 뒤 별도로 배치

> **검색 3회 제한은 사고 대응으로 추가됐다.** 초기 규칙이 수치를 강하게
> 요구하자 Claude가 지산 실거래가를 찾느라 웹 검색을 7~8회 반복했고,
> 토큰 한도를 다 써서 본문을 한 글자도 못 쓴 채 잘렸다.

### A5-4. 그 밖의 규칙

- 표에서 열을 나눌 때는 각 열의 값이 실제로 달라야 함.
  데이터에 구분이 없어 같은 값이 반복되면 열을 하나로 합칠 것
- 각 섹션은 앞 섹션에 없던 새 내용을 더할 것.
  같은 확인 항목을 체크리스트·판단기준·지역섹션에서 세 번 반복하지 말 것
- 계산기 링크는 프롬프트에 실제 주소가 주어졌을 때만.
  URL 없이 `[계산기 링크]` 자리표시자를 만들지 말 것
- 이미지는 정확히 2곳, `[이미지: 한글설명 | search: 영어검색키워드]` 형식.
  **`| search:` 뒤 영어 키워드는 필수**이며, 지역명 없이 보편적인 장면으로.
  (좋은 예: modern office interior / 나쁜 예: dongtan technovalley)
- 한 문단 최대 3~4줄 / 나열 정보는 불릿 / 섹션 핵심 결론은 볼드
- 전문 용어는 첫 등장 시 괄호로 쉬운 설명 병기
- 근거 링크는 해당 문단 바로 아래 `>` 인용으로 배치
- 출처는 공식 출처만. **나무위키·위키백과·개인 블로그·상업 시세 사이트 금지**
- 표의 숫자 열은 우측 정렬, 소수점 자릿수 통일, 천 단위 쉼표

### 스코어 공식을 뒤집었다 — 2026-09-21

옛 공식은 관심도를 잰다고 했지만 실제로는 **경쟁도**를 재고 있었다.

```
옛:  트렌드 50% + 블로그 건수 30% + 카페 건수 20%
```

**트렌드지수가 0인 키워드가 많다**(데이터랩이 검색량 부족 시 0 반환).
그러면 점수가 문서 수로만 결정되는데, **문서가 많다는 건 경쟁이 심하다는 뜻**이지
관심이 높다는 뜻이 아니다. 경쟁 낮은 롱테일을 노린다는 A8 전략과 정반대다.

2026-09-21 실측이 그 증거다.

| 키워드 | 블로그 | 카페 | 옛 점수 | 카페÷블로그 |
| --- | ---: | ---: | ---: | ---: |
| 지식산업센터 등기부 확인 | 40,417 | 88,225 | **0.39 (1위)** | 2.2 |
| 동탄 지식산업센터 전용률 | 11,484 | 196,290 | 0.284 | 17.1 |
| 동탄 지식산업센터 실거래가 | 4,663 | 197,086 | **0.235 (꼴찌)** | **42.3** |

**카페는 질문이 쌓이는 곳이고 블로그는 답이 쌓이는 곳이다.**
실거래가는 질문이 답의 42배인데 점수는 꼴찌였다. 순서가 정확히 거꾸로였다.

```
새:  기회 = 카페 건수 ÷ 블로그 건수          (질문 ÷ 답)
     점수 = 기회 정규화 × 0.6 + 트렌드 × 0.4
```

트렌드는 0이 흔해서 주 신호로 못 쓴다. **있을 때만 가산**한다.
트렌드가 전부 0이어도 기회 비율만으로 줄이 제대로 선다.

### 풀과 쿨다운 — 점수와 순환을 겹친다

점수 1위만 보면 같은 키워드가 계속 뽑혀 소재가 굳는다(지역 트랙이
"동탄 서울"로 네 번 연속 나갔던 그 문제다). 순환만 하면 기회가 없는
키워드도 차례가 되면 그대로 나간다. 그래서 둘을 겹쳤다.

```
① 기회 점수 내림차순 정렬
② 상위 KEYWORD_POOL(4)개만 후보 풀        ← 품질 하한선
③ 최근 KEYWORD_COOLDOWN(2)회 쓴 것 제외   ← 고착 방지
④ 남은 것 중 1위
```

| 손잡이 | 하는 일 |
| --- | --- |
| `KEYWORD_POOL = 4` | **하한선.** 5·6위는 점수가 올라야 들어온다 |
| `KEYWORD_COOLDOWN = 2` | **순환 폭.** 상위 3개가 돈다 |

**쿨다운이 순환 폭을 정한다 — 최근 N개를 빼면 상위 N+1개가 돈다.**
풀 크기는 그 위 한계선일 뿐이다. 4위를 순환에 넣으려면 풀을 키우는 게
아니라 쿨다운을 3으로 올려야 한다. 12회 돌려 확인했다.

```
POOL=4 COOLDOWN=2  →  실거래가 → 전용률 → 시세 → 실거래가 → …   (상위 3개)
POOL=5 COOLDOWN=3  →  실거래가 → 전용률 → 시세 → 매매 → …        (상위 4개)
```

**쿨다운은 주가 아니라 '그 카테고리를 몇 번 방문했는지'로 센다.**
같은 카테고리가 3주에 한 번 오므로 주 단위로 세면 쿨다운이 무의미해진다.
이력은 `state/keyword_history.json` 에 카테고리별로 쌓인다.

**목요일 지역 트랙은 이 계산을 쓰지 않는다.** 현안명이 곧 소재라
점수와 무관하게 고정된다(A9 참조).

## A8. 경쟁 현황과 초기 전략

### 경쟁 글의 공통 약점 = 우리의 진입점

상위 글은 최근 글이고 광고성 매물 글도 아니다. 그러나 **숫자가 하나도 없다.**
투자 글인데 평당 분양가도, 임대료 시세도, 수익률 계산도 없이
"공실이 길어지면 수익이 달라질 수 있다" 같은 조건부 서술뿐이다.

읽고 나서 **독자가 무엇을 해야 할지 알 수 없다.**

> 이 진단이 [A5 톤앤매너](#a5-톤앤매너)의 금지 표현 목록을 만든 근거다.
> 정확히 그 반대로 쓰면 된다 — **구체적 숫자 + 실행 가능한 도구.**

### 초기 전략

1. **경쟁 낮은 롱테일로 글을 쌓아 블로그 지수를 올린다**
   (동탄상가분양, 동탄지식산업센터임대, 동탄공장매매)
2. **실거래·경매 데이터로 대체 불가능한 콘텐츠를 만든다**
3. 글이 10편 이상 쌓인 뒤 `동탄지식산업센터` 대형 키워드에 도전

완료된 것도 행은 남긴다. 나중에 되살릴 수도 있고,
"이 사업은 2028년에 끝났다"는 기록 자체가 자산이다.

### 순환 규칙

```
① state/agenda_last_id.txt 의 다음 id부터 시작
② 활성 안건만 대상 (보류·완료는 건너뛴다)
③ 각 안건마다 신선도 판정 → 진전 있으면 선택, 없으면 다음으로

### 고시 연표 — 2026-09-17 추가

현안에 걸리는 화성시 고시를 공고일 순으로 최대 10건 모아 프롬프트에 넘긴다.
고시 제목에는 행정 절차가 그대로 드러나므로, 시간순으로 늘어놓으면
그 자체가 '지금까지의 흐름' 섹션의 1차 재료가 된다.

```
열람·의견청취·공람  → 심의 전
결정 고시·지형도면   → 확정
실시계획 인가        → 착공 직전
재결·수용·보상계획   → 보상 단계
준공·사용승인        → 완료
```

**조회 기간은 5년(`NOTICE_DAYS = 1825`)이다.** 백필이 가져오는 것은 대부분
몇 년 전 고시라, 1년으로 잡으면 결과가 통째로 잘린다. 10건이 넘으면
최신 9건에 **가장 오래된 1건**을 붙인다. 그 하나가 사업의 시작점이다.

**지역 필터** — 현안명에 "동탄"·"장지동"·"영천동"·"오산동"이 들어가면
`동탄관련 = O` 인 고시만 넘긴다. "동탄 주택공급" 글에 남양뉴타운 고시가
재료로 들어가면 글이 통째로 어긋난다. 실제로 그 일이 있었다(D3 참조).

**지어내기 금지** — 고시 목록에 있는 것은 공고일과 제목뿐이다.
입주 시점·준공일·세대수·사업비는 주어지지 않는다. 기획·초안 양쪽
프롬프트에 "주어지지 않은 것을 추정해 쓰지 말 것"을 명시한다.
승인일을 입주 시기로 읽는 사고가 실제로 있었다.

### 중기지방재정계획 — 2026-09-19 설계 · **2026-09-20 설치 완료**

고시는 "결정했다"를, 회의록은 "논의 중이다"를 알려준다.
재정계획은 그 둘에 없는 것을 알려준다 — **언제 얼마를 쓸 계획인가.**

```
도시철도 건설사업        기간 2019.05~2028.12
   총 1조 701억 · 기투자 1,247억 · 향후 9,454억
   2026년 700억 → 2027년 4,497억 → 2028년 4,257억 → 이후 0
```

9/17 트램 글에서 회의록 근거로 쓴 **총사업비 9,982억**과 숫자가 다르다.
이런 대조는 고시로도 회의록으로도 못 한다.

| | |
| --- | --- |
| 원문 | `data/plans/` 에 **PDF 를 그대로** 넣는다 |
| 색인 | `index_plans.py` → `data/plan_projects.csv` |
| 매칭 | `collect_sources.py` `load_plans()` — 현안 키워드 |
| 실행 | Actions → 재정계획 색인 (index-plans) · `check_only` 로 미리보기 |
| 현재 | 경기도 1,549건(억원) + 화성시 1,635건(백만원) = **3,184건** |
| 소요 | 25MB PDF 포함 5분 56초. 20분 제한 안이다 |

**파싱 앵커는 `기간:` 이 든 줄**이다. 그 위가 사업명, 아래 첫 `계` 가 금액.
부문 요약줄도 "이름 + 숫자 9개" 형태라 그것만으로는 사업과 요약을 못 가른다.
경기도 파일은 `기간:` 라벨 없이 날짜만 있는 경우가 많아 둘 다 앵커로 받는다.

**PDF 추출기를 둘 다 돌린다.** pypdf 와 pdfplumber 는 줄바꿈 자리가 달라,
같은 문서도 어느 쪽은 사업이 잡히고 어느 쪽은 안 잡힌다.
앵커가 많이 잡히는 쪽을 쓰고, 뽑아낸 원문은 `data/plans/_extracted/` 에 남긴다.

**그 판단이 화성시 파일을 통째로 살렸다 (2026-09-20 실측).**

```
경기도  pypdf 570,976자 · 앵커 1,643   pdfplumber 551,480자 · 앵커 1,424
화성시  pypdf 645,986자 · 앵커 1,729   pdfplumber 635,654자 · 앵커     1
```

화성시 PDF 에서 pdfplumber 가 앵커를 **한 개**밖에 못 잡았다. 로그에
`Advanced encoding /UniKS-UTF16-H not implemented yet` 가 수백 줄 찍히는데,
내부 pdfminer 가 한글 CID 폰트 인코딩을 모른다는 뜻이다.
추출기를 하나만 썼다면 1,635건이 통째로 날아갔다.

**금액 열은 아홉 개이고, 배치가 헷갈린다.**

```
총사업비 | 기투자 | [연도별투자계획: 소계 2026 2027 2028 2029 2030] | 향후
   433      23         308    0  103  103  103    0          103
```

세 번째 숫자는 **향후가 아니라 5년 소계**다. 진짜 향후(2031년 이후)는 맨 끝에 있다.
트램은 2031년 이후가 0이라 두 값이 우연히 같아 보였고, 그래서 한동안 못 잡았다.
장지-남사처럼 5년을 넘기는 사업에서는 103억이 통째로 사라진다.

검산은 `총사업비 = 기투자 + 5년소계 + 이후` 로 한다.

```
   433 ≈    23 +   308 + 103     (반올림 오차 1)
   322  =     2 +   320 +   0
10,701  = 1,247 + 9,454 +   0     ← 트램. 화성시 파일도 같은 구조
```

**조치** — `향후` 열에 `소계 + 이후` 를 넣고 `이후` 열을 따로 뒀다.
그러면 `향후` 가 말 그대로 "앞으로 쓸 돈"(= 총사업비 − 기투자)이 되어
`collect_sources.py` 와 프롬프트는 손댈 게 없다.

**사업명은 공백 없이 잇는다.** PDF 표의 좁은 칸에서 단어 중간에 줄바꿈이
들어가므로 조각을 공백으로 이으면 `국지도건 설`·`교 체`·`지원사 업` 이 된다.
`"".join()` 으로 바꾸니 19건 중 18건이 제대로 붙었다. 단어 경계에서 끊긴
하나(`비점오염저감시설유지관리`)는 반대로 붙지만 규칙으로는 더 가를 수 없다.

**단위가 파일마다 다르다.** 경기도는 억원, 화성시는 백만원이다.
머리말에서 읽어 **억원으로 통일**해 넘긴다. 그대로 넘기면
`1,070,101` 이 1조인지 107만원인지 모델이 헷갈린다.

**프롬프트에 박은 경계 셋**

```
계획은 배정이지 확정이 아니다
   "2028년에 4,257억이 잡혀 있다" 맞음
   "2028년에 4,257억을 쓴다"      틀림
집행 진도는 공정률이 아니다 — 돈과 공사는 다르다
숫자가 어긋나면 그대로 쓴다 — 출처를 밝혀 나란히
```

네이버 정적지도는 NCP 콘솔에서 **Maps 상품을 신청**해야 쓸 수 있다
(2026-09-17 확인: `Permission Denied 210` — 인증은 맞고 상품만 미신청).
신청하면 `draw_map()` 하나만 바꾸면 되고 부르는 쪽은 손대지 않는다.

좌표는 Plus Code 로 넣는 것이 편하다. 네이버·구글 지도에서 지점을 길게 눌러
얻은 코드를 `scripts/pluscode.py` 로 변환한다. A002 와 A005 를 그렇게 넣었다.

> **Plus Code 는 반드시 풀어서 확인한다 (2026-09-20).**
> A006 좌표를 받는 과정에서 코드가 두 번 연속 엉뚱한 곳을 가리켰다.
> 한 번은 태평양(위도 22.78), 한 번은 남양주 방면(위도 37.78)이었다.
>
> 눈으로 거르는 법이 있다. **동탄·남사 일대는 전체 코드가 `8Q99` 로 시작하고,
> 짧은 코드가 `54` 또는 `55` 로 시작한다.** 앞 두 글자만 봐도 걸러진다.
> 이 범위를 벗어나면 그 코드는 이 동네가 아니다.
>
> 더 확실한 것은 **위도·경도 숫자를 그대로 받는 것**이다. 구글맵에서 지점을
> 길게 누르면 `37.1823, 127.1345` 가 그대로 뜬다. 변환 과정이 없으니
> 틀릴 여지도 없다. 선형 현안은 여기에 더해 **끝점 사이 직선거리가
> 사업 연장보다 길지 않은지** 검산한다. 도로가 직선보다 짧을 수는 없다.

### 선형 지도 — 2026-09-20 신설

도로·철도처럼 **선으로 놓인 현안은 핀 하나로 뜻이 안 통한다.**

**좌표를 모르는 지형지물은 핀을 안 찍는다.** 함봉산이 그렇다. 대신 선 가운데에

지나므로, 좌표를 지어내지 않고도 참인 표시다.

**이름표는 선 방향 바깥으로 민다.** 가운데에 몰아 두면 양끝 이름과 구간설명이

방향 벡터를 그만큼 나눈 뒤 쓴다.

**선형일 때 `위도`·`경도` 도 함께 채운다.** 그림은 `agenda_lines.csv` 로
그리지만, `build_agenda_material()` 이 **지도 안내 문구를 넣을지 정할 때

모델은 붙는 줄을 몰라, 위치를 글로 길게 풀어 쓰고 "개념도라 거리를 단정하지

**키는 (시군구, 법정동, 지번) 세 개다.** 다른 시군구에 같은 법정동명이
있어서, 시군구를 빼면 서로 다른 건물이 한 덩어리로 뭉친다.

**유형** : 지산 / 오피스 / 오피스텔 / 연구시설 / 아파트 / **제외**
`제외`는 노인복지주택처럼 지산·상가와 시장이 다른 건물. 분석에서 통째로 뺀다.

**입지 블록** (산업 성격 기준으로 통일)

```
동탄 테크노밸리 / 동탄 삼성전자화성 / 동탄 지원시설(ASML) / 동탄 지원시설(동탄역)
기흥 지산벨트 / 기흥 도시첨단산업단지 / 기흥 일반상권
```

행정·교통 시설 기준(기흥세무서, 강남대역 등)으로 나누면
"이 물건이 어떤 산업 배후에 있나"를 못 본다. 반드시 산업 성격으로 묶는다.

### 자동 분류

매핑에 없는 지번은 `buildingUse`로 유형만 추정한다.
근린생활→근린상가, 판매→판매시설, 교육연구, 숙박, 공장, 창고.
**`업무`는 지산/오피스 구분이 불가**해 `업무(미확인)`으로 두고 수동 확인 대상으로 뽑는다.

이 덕분에 **유형별 집계는 100% 커버**되고, 수동 작업은 업무시설만 하면 된다.

## B3. 지역 이슈 키워드 (구글 뉴스)

| 항목 | 내용 |
| --- | --- |
| 출처 | 구글 뉴스 RSS (`news.google.com/rss/search`) |

**네이버 뉴스 API는 401**이 떠서 못 쓴다(별도 신청 대상).
구글 뉴스 RSS는 인증이 필요 없고 User-Agent만 붙이면 된다.

### 3단계 필터

```
1. 씨앗 질의 7개로 최근 3주 기사 수집
   "동탄 지식산업센터", "동탄 산업단지", "동탄 반도체 클러스터",
   "화성 동탄 개발계획", "동탄 교통망 착공", "동탄 상업용지", "동탄 부동산 시장"
   → "동탄 개발"처럼 넓게 잡으면 생활·연예 기사가 대량으로 딸려온다

2. EXCLUDE_WORDS 로 통째로 버림
   패밀리풀·물놀이·축제·맛집·연예·행사·개최 등
   → 부동산 문맥어가 섞여 있어도 무조건 제외

3. CONTEXT_WORDS 가 없으면 버림
   분양·매매·임대·지식산업센터·산업단지·클러스터·착공 등
```

### 트렌드 검증

형태소 분석기 없이 낱말을 뽑으면 이상한 게 섞인다.
그래서 `"동탄 OO"` 형태로 만들어 **검색어 트렌드가 0보다 큰 것만** 인정한다.

### 승인 절차

발굴된 후보를 텔레그램으로 보내고, **뺄 것만 지정**하는 방식이다.

```
뺄 것은 -번호로 답장해주세요. 예) -1 -4 -11
직접 추가하려면 +키워드. 예) +동탄 트램
(10분 안에 무응답이면 전부 사용합니다)
```

신규 키워드는 기본값이 `pinned: true`. 일일이 켤 필요 없이 뺄 것만 고른다.
`+키워드`로 직접 추가한 것은 `manual: true`가 붙어 자동 은퇴하지 않는다.
60일 넘게 뉴스에 안 나오면 자동 은퇴한다(GTX가 개통되면 알아서 사라진다).

### 기사 제목도 재료로 쓴다

키워드만 넘기면 Claude가 웹 검색으로 다시 찾아야 한다.
수집한 제목 60건을 `local_headlines.json`에 저장해 초안 프롬프트에 함께 넘긴다.

### 배제가 우선순위를 이긴다 — 2026-10-01

범위를 넓히자 **복지 항목이 섞여 들어왔다.**

```
아빠 육아휴직 장려금 12억 6,000만 전액 삭감, 도비 미확보로 …
경기도 산후조리비 등 4개 사업 일몰에 대해 시 자체 대응안 미흡 …
```

금지 목록에 `복지`가 있는데도 들어왔다. 우선순위 2번의 **"감액"** 이
금지보다 세게 작동한 것이다 — 전액 삭감은 감액이니까.

배제를 우선순위 **위**로 올리고, 실제로 걸린 사례를 그대로 적었다.

```
**위 우선순위에 해당하더라도 이 분야면 담지 마라.**
예를 들어 육아휴직 장려금이 전액 삭감된 것은 우선순위 2번의 '감액'이지만,
이 글의 독자(동탄에서 사업장을 찾는 사람)와 아무 관계가 없다.
감액·삭감이라는 말에 끌려가지 마라.
```

추상적 금지보다 **구체적 반례**가 잘 듣는다.

### 요약이 넉 달 가까이 실패하고 있었다 — 2026-10-01 해결

9/15 예산결산특위 제4차(86,702자)의 요약이 계속 실패해 매일 발췌가
날아왔다. 원인을 세 번 틀리게 짚은 뒤에야 잡았다.

| 추측 | 실제 |
| --- | --- |
| 1차: `max_tokens` 1200 절단 → 3000 으로 | 맞았지만 3000도 부족했다 |
| 2차: 입력 15만 자 초과 → 줄여서 재시도 | 86,702자라 한도 안이었다 |
| 3차: **출력 한도 8,000** (끊기면 2차 16,000) | 성공 |

로그가 판정했다.

```
요약 시도 1/2 — 회의록 86,702자 중 86,702자 넘김   ← 입력은 한도 안
요약 실패: 응답이 max_tokens 에서 끊겼습니다        ← 모자란 것은 출력
```

**재시도 조건이 실패 종류에 따라 갈려야 한다.** 입력이 길어 거절당한
것과 출력이 모자라 끊긴 것은 정반대 처방이다.

| 1차 실패 | 2차 조건 |
| --- | --- |
| `max_tokens` 절단 | 입력 그대로, **출력 2배** |
| `HTTP 400 ... too long` | **입력 축소**, 출력 그대로 |
| 타임아웃·429 | 같은 조건으로 재시도 |

입력을 줄일 때는 앞에서 자르면 안 된다. **가결·부결과 시정요구사항은
회의 마지막에 나온다.** `shrink_for_summary()`가 적중 구간을 점수순으로
모으고 **회의 끝 8,000자를 반드시 붙인다.** 8만 자를 2만 자로 줄여도
적중어와 의결 결과가 보존된다.

프롬프트에도 한 줄 넣었다. 요약은 어차피 600자로 잘려 저장되므로
**길게 써봐야 뒤가 버려진다.**

```
한 줄은 100자 안쪽으로 쓴다. 요약 전체는 600자까지만 저장되므로
길게 쓰면 뒤가 잘려 오히려 내용을 잃는다.
```

### 같은 회의록이 매일 날아왔다 — 2026-09-30 해결

요약이 실패하면 발췌를 보내고 넘어가는데, **그 분기만 `요약` 칸을
채우지 않았다.** 다른 세 분기(적중어 없음·개발어 미적중·담을 논의 없음)는
모두 `"없음"`을 박아 자기종료하는데 여기만 빠졌다. 빈 칸으로 저장되면
다음 실행의 "다시 보는 회의" 목록에 또 들어가 끝없이 되풀이됐다.

열 두 개를 더했다.

| 열 | 쓰임 |
| --- | --- |
| `알림일` | 한 번 알렸으면 다시 안 보낸다 |
| `요약시도` | 2회 실패하면 `없음(요약 실패 2회)` 로 확정해 순환을 끊는다 |

선별 로직은 `main()` 에서 `pick_again()` 으로 빼냈다. 묻혀 있으면
시험할 수 없어서다. 6일 연속 실행 시험에서 알림이 6회 → 1회가 됐다.

### ⚠️ 파일 간 동기화 주의점

**① HTML 렌더링 함수** — `generate_draft.py`와 `check_and_publish.py`의
`generate_score_chart_base64` ~ `render_naver_html`을 **완전히 동일하게** 유지.

**② 콘텐츠 규칙** — `content_rules.py` 한 곳만 고치면 양쪽에 반영된다.
그중 `CRITERIA_RULES`(판단 기준)는 **세 관문이 공유한다** — 기획
(`generate_plan.py`), 초안(`generate_draft.py`), 검증(`verify_draft.py`).
기획 스크립트가 이것을 안 보고 있어서 09-30 수정이 1차 관문에
닿지 않았던 적이 있다(A3-2 참조).

**②-2 날짜** — `date_guard.today_kst()` 하나만 쓴다. GitHub Actions 가
UTC 로 돌아 `date.today()` 를 그냥 쓰면 KST 오전이 전날로 나온다.

```python
from content_rules import build_rules
rules = build_rules(category)     # jisik / sangga / local / realprice / auction
```

**③ 트랙 값 전달** — `collection_result.json`의 `track`을 읽어 넘겨야
트랙별 톤과 해시태그가 맞는다.

```python
track = result.get("track", "jisik")
prompt = build_prompt(result, refs, today, plan=plan, category=track)
```

**④ 스케줄러는 하나뿐이다** — 요일·주차 분기는 `collect_sources.py`의
`pick_track()` **한 곳에서만** 한다. `content_rules.py`에 있던 `pick_theme()`은
호출되지 않는 죽은 코드였고 실제 동작과 달라 혼선을 일으켰다.
스케줄을 고칠 때는 `pick_track()`만 본다.

**⑤ 아젠다는 collect 단계에서 확정된다** — `generate_plan.py`와
`generate_draft.py`는 `collection_result.json["agenda"]`를 **읽기만** 한다.
현안 선정 로직을 기획·초안 쪽에 넣지 않는다.

**⑥ 코드가 본문에 직접 문장·그림을 넣는 지점** — 프롬프트를 아무리 고쳐도
이것들은 안 바뀐다. 따로 목록으로 관리한다.

| 위치 | 무엇 | 트랙 |
| --- | --- | --- |
| `render_naver_html` 도입 문구 | H1 아래 한 문단 | 전 트랙 (문구는 트랙별로 다름) |
| `render_naver_html` 지도 | 위치 개념도 | `local` 만 |
| `build_score_table_html` | 관심도 표 | 전 트랙 (맨 아래) |
| `render_images` | Unsplash 사진·스코어 차트 | 전 트랙 |

**⑦ 텔레그램 답장을 기다리는 워크플로는 서로 겹치면 안 된다** —
`getUpdates` 는 먼저 폴링한 쪽이 가져간다. 같은 시각에 둘이 기다리면
답장이 엉뚱한 쪽으로 들어간다. 현재 답장을 기다리는 것은 셋이다.

| 워크플로 | 시각 | 대기 |
| --- | --- | --- |
| 현안 점검 | 1·15일 09:31 | 10분 |
| 기획안 | 월·목 08:17 이후 | 5분 |
| 승인 확인 | 15분마다 | 즉시 |

업체 DB 알림(Part E)은 **발송 전용**이라 답장을 읽지 않는다. 충돌하지 않는다.

## C5. 초안 검증

`verify_draft.py`가 초안 생성 직후 돌면서 두 겹으로 확인한다.

### 형식 검사 (Claude 없이)

| 항목 | 기준 |
| --- | --- |
| 분량 | 2,000~3,600자 |
| 해시태그 | 5개 이상 |
| 금지 표현 | `~할 수 있습니다`, `전문가와 상담` 등 |
| 이미지 | 정확히 2곳 |
| 계산기 링크 | 기획안의 `calc_tab`과 일치하는가 |
| 자리표시자 | `<mark>[...]</mark>` 남은 개수 |
| 표 | 존재 여부 |

### 의미 검사 (Claude) — 11가지, 2026-10-01 확장

```
 1 독자 일치        다른 독자용 내용이 섞였는가 (특히 계산 예시)
 2 산출물 일치      기획한 도구가 실제로 있는가
 3 핵심 결론 일치   서두에 제시되고 본문이 뒷받침하는가
 4 판단 기준 반영   3가지가 다 나오는가  ← 일치 여부만 본다
 5 문단별 정합성    기획과 무관한 문단이 있는가
 6 중복             같은 내용이 반복되는가
 7 시점 정합성      지난 날짜를 미래형으로 썼는가
 8 기사 나이와 톤   오래된 근거에 "최근"을 붙였는가
 9 데이터 구분 이름  표에 없는 항목을 본문이 말하는가      ★ 신설
10 적은 표본 표기    10건 미만에 건수와 참고치 표시가 있는가  ★ 신설
11 판단 기준의 타당성  기준 자체가 성립하는가               ★ 신설
```

**9·10번은 원래 있었는데 돌지 않았다.** 프롬프트는 10개 항목을
판정하라고 했는데 **JSON 출력 자리가 8개뿐이었다.** 쓸 곳이 없으니
조용히 사라졌다. 예시 JSON에는 쉼표도 두 곳 빠져 있어 그대로
파싱하면 깨졌다.

```
요구 11개 / 자리 8개 → 3개가 출력될 곳이 없다
```

그 둘이 돌았다면 10-01 초안의 `동탄 지원시설(ASML) 블록(6건)` —
표에 없는 항목에 10건 미만 — 을 잡았을 것이다.
지금은 selftest 가 `vp.count('"name"') == 11` 로 자리 수를 센다.

**11번이 가장 중요하다.** 4번은 기획안과 **같은지만** 본다.
기획이 출처 없는 "3배"를 넣으면 초안이 그대로 베끼고 검증은
"동일하다"를 합격 근거로 쓴다. 11번은 기획안에 있던 기준이라도
`CRITERIA_RULES` 에 걸리면 **실패**로 판정한다.
4번 설명에도 못 박았다 — *"여기서 '통과'가 기준이 타당하다는 뜻은 아니다."*

### 수정 요청 문장을 만들어준다

리포트 맨 아래에 **그대로 답장하면 반영되는 문장**이 나온다.

**자동 재생성은 하지 않는다.** 비용이 크고, 검증기가 틀렸을 때
멀쩡한 초안을 망칠 수 있다. 알려만 주고 판단은 사람이 한다.

### 날짜는 KST 로 — 2026-10-01

검증기가 **맞는 날짜를 틀렸다고 지적한 일**이 있었다.

```
× 시점 정합성 — 기준일이 2026-09-30인데 본문에 '오늘(2026-10-01)'로 명시되어
```

그날은 10월 1일이었다. `date.today()` 가 UTC 를 돌려주는데 GitHub
Actions 는 UTC 로 돌고, **KST 오전은 UTC 로 전날**이다. 초안은
`today_kst()` 를 쓰는 `generate_draft.py` 가 만들어 10-01 을 정확히
썼는데, 검증기만 다른 날짜를 보고 있었다.

더 나쁜 것은 그 오진이 **"가장 시급한 것"과 "수정 요청 문장"에까지**
올라갔다는 점이다. 그대로 답장하면 맞는 날짜가 틀린 날짜로 바뀐다.

`date_guard.today_kst()` 를 두고 날짜가 필요한 곳이 그것을 쓴다.
프로세스 시간대가 UTC 든 Midway 든 Kiritimati 든 같은 날짜가 나온다.

```python
KST = timezone(timedelta(hours=9))
def today_kst():
    return datetime.now(KST).date()
```

환경변수 `TZ` 를 고정하는 방법도 있지만 `os.environ.setdefault` 는
**TZ 가 이미 있으면 덮지 않는다.** 누가 워크플로에 `TZ` 를 한 줄
넣는 순간 다시 틀린다. 안전망으로만 남기고 날짜는 함수로 가져온다.

### 기사 나이 검사의 오탐 — 2026-10-01

```
! 기사 나이 — 신선도 표현 1곳: '오늘' → …오늘(2026-10-01) 기준 1년 넘게…
○ 기사 나이와 톤 — 외부 뉴스 기사를 인용하지 않았으므로 해당 없음
```

한 리포트 안에서 두 항목이 서로 모순됐다. 기계 검사가 '오늘'이라는
낱말만 보고 경고했고, 모델 검사가 맥락을 보고 부정했다.

- `오늘(2026-10-01) 기준` 은 **기준일 표기**다. 새 소식 주장이 아니다.
  `_ASOF_AFTER` 로 신선도 낱말 뒤에 날짜가 붙으면 면제한다
- 근거 날짜가 없으면 기계 검사는 **침묵**한다. 판정할 수 없는 것을
  "확인하세요"로 내보내지 않는다

`check_recency` 가 `__main__` 블록보다 **아래에** 정의돼 있어
자체 테스트가 한 번도 돌지 않은 것이 원인이었다. 블록을 파일 끝으로
옮기고 기사 나이 테스트 6건을 보탰다. 지금 15/15 통과한다.

### 실제로 잡아낸 것들

- "더 읽어보기" 링크가 행복주택·재건축 아파트로 주제와 무관
- 부가세 환급 기간이 같은 글에서 "1~2개월"과 "15~20일"로 불일치
- 핵심 결론은 "대출이자를 더한 총액"인데 표에서는 순수익에서 차감
- 순서 안내 글에 임대수익률 계산이 끼어들어 흐름 단절

## D3. 트러블슈팅 이력

### 규칙이 함정을 가르치고 있었다 (2026-10-01)

실거래 기획안에 `"매물이 평균 거래건수의 3배를 넘는지"` 라는 판단 기준이
나왔다. 출처 없는 숫자였다. 모델 탓으로 보였지만 아니었다.

`content_rules.py` 가 판단 기준의 **예시로** 이렇게 적고 있었다.

```
(예: "전용률 50% 미만 -> 실사용 부적합", "역까지 도보 10분 초과 -> 임차 수요 약함")
```

50%도 10분도 출처가 없다. 더 나쁜 것은 1차 관문이었다.
`generate_plan.py` 는 같은 예시를 `"~는 좋습니다"` 라는 권장형으로 들고
있었다.

**조치**: `CRITERIA_RULES` 를 상수로 떼어 세 관문이 공유하게 했다.
상세는 A3-2.

**교훈**: **프롬프트에 적은 예시는 곧 지시다.** 금지하려는 것을 예시로
들면 그것을 가르치는 셈이 된다. 그리고 **고친 규칙이 모든 관문에
닿는지 확인한다** — 기획 스크립트는 `content_rules` 에서 세 가지만
가져다 쓰고 있어서 수정이 전혀 반영되지 않았다.

### 지워야 할 예시를 설명으로 남겼다 (2026-10-01)

위 예시를 걷어내면서 `"예전 이 자리에는 … 이 예시로 적혀 있었다"` 라고
규칙 문자열 안에 기록을 남겼다. 자체 검사에 걸렸다.

`CONTENT_RULES` 는 프롬프트다. **지워야 할 예시를 '예전엔 이랬다'며
남기면 모델에게는 여전히 예시로 보인다.**

**교훈**: 프롬프트는 모델에게 주는 지시, 주석은 사람에게 남기는 기록.
섞지 않는다.

### 검증기가 맞는 날짜를 틀렸다고 지적했다 (2026-10-01)

```
× 시점 정합성 — 기준일이 2026-09-30인데 본문에 '오늘(2026-10-01)'로 명시되어
```

그날은 10월 1일이었다. `date.today()` 가 UTC 를 돌려주고 KST 오전은
UTC 로 전날이다. 초안은 `today_kst()` 를 써서 맞았는데 검증기만
틀렸다.

그 오진이 **"가장 시급한 것"과 "수정 요청 문장"에까지** 올라갔다.
그대로 답장하면 맞는 날짜가 틀린 날짜로 바뀐다.

**조치**: `date_guard.today_kst()` 를 두고 날짜가 필요한 곳이 쓴다.

**교훈**: **검증기도 틀린다.** 검증기가 내놓은 수정 요청을 그대로
보내기 전에 한 번은 본다. 그리고 **같은 저장소의 두 스크립트가 다른
날짜를 보고 있지 않은지** 확인한다.

### 요구한 검사 항목이 조용히 사라졌다 (2026-10-01)

`verify_draft.py` 의 프롬프트는 **10개 항목**을 판정하라고 했는데
JSON 출력 자리는 **8개**뿐이었다. 9·10번은 쓸 곳이 없어 사라졌다.
예시 JSON 에는 쉼표도 두 곳 빠져 있었다.

그 둘이 돌았다면 그날 초안의 `동탄 지원시설(ASML) 블록(6건)` —
표에 없는 항목에 10건 미만 — 을 잡았을 것이다.

**조치**: 자리를 11개로 맞추고, selftest 가 `vp.count('"name"') == 11`
로 자리 수를 센다.

**교훈**: **지시와 출력 형식의 개수가 맞는지 센다.** 안 맞으면
뒤쪽 지시가 조용히 버려지고, 로그에 아무것도 남지 않는다.

### 검사가 성립하지 않는 것을 "확인하세요"로 내보냈다 (2026-10-01)

한 리포트 안에서 두 항목이 서로 모순됐다.

```
! 기사 나이 — 신선도 표현 1곳: '오늘' → …오늘(2026-10-01) 기준…
○ 기사 나이와 톤 — 외부 기사를 인용하지 않았으므로 해당 없음
```

기계 검사가 '오늘'이라는 낱말만 보고 경고했고 모델 검사가 부정했다.
`오늘(2026-10-01) 기준` 은 기준일 표기이지 새 소식 주장이 아니다.

원인은 더 깊었다. `check_recency` 가 `__main__` 블록보다 **아래에**
정의돼 있어 **자체 테스트가 한 번도 돌지 않았다.**

**교훈**: 테스트 블록 아래에 함수를 정의하면 그 함수는 테스트를
안 받는다. 그리고 **판정할 재료가 없으면 침묵한다** — 확인할 수 없는
것을 "확인하세요"로 내보내면 사람이 경고에 둔감해진다.

### selftest 가 절반을 안 보고 있었다 (2026-10-01)

**교훈**: **스크립트를 새로 만들면 selftest 목록에도 넣는다.**
"모두 통과"가 "모두 검사했다"는 뜻은 아니다.

**교훈**: **원인을 모르면 추측하지 말고 로그부터 고친다.**
에러 본문, 입력 크기, 출력 한도를 찍게 한 뒤 한 번 돌리면 끝날 일을
세 번 추측했다. 그리고 **재시도 조건은 실패 종류에 따라 갈려야 한다** —
입력이 길어 거절당한 것과 출력이 모자라 끊긴 것은 정반대 처방이다.

### 참고링크 필터가 지역만 보고 있었다 (2026-10-01)

`"동탄 지식산업센터 매매"` 로 검색한 글에 `"동탄상가주택 매매"` 가

| 증상 | 원인 |
| --- | --- |
| `IndentationError` | 공백 개수 어긋남 |
| **에러 없이 아무 동작 안 함** | `if __name__` 블록이 `main()` 안으로 들어감 |
| `SyntaxError: 'return' outside function` | 함수 내부 줄의 들여쓰기가 풀림 |

> ```python
> if __name__ == "__main__":
>     main()
> ```

**교훈**: 웹 편집기로 고친 뒤에는 반드시 실행해서

### 카테고리 번호를 키워드 번호로 재사용해 순환이 멈춰 있었다 (2026-09-21)

### 붙여넣은 블록이 `return` 뒤에 붙었다 (2026-09-20)

```python

    return "\n".join(lines)        ← 여기서 함수가 끝난다

**조치**: 교체 범위를 `if a.get("위도")` 부터 다음 `def` 직전까지로 잡고

**교훈**: 함수에 블록을 더할 때는 **`return` 이 어디 있는지 먼저 본다.**
그리고 붙여넣기 전에 **교체 범위의 끝**을 정한다. 시작만 정하면 끝이 흐른다.

### cron 이 하루 밀려 돌고 있었다 (2026-09-19 발견)

`discover-keywords.yml` 의 주석에는 이렇게 적혀 있었다.

```yaml
- cron: '31 22 1,15 * *'   # 매월 1일·15일 07:31 KST
```

**실제로는 2일·16일에 돌고 있었다.** 22:31 UTC 는 KST 로 다음 날이다.

```
UTC 10-01 22:31  →  KST 10-02 07:31
```

KST 아침 시각을 UTC 로 옮기면 날짜가 하루 당겨진다.
**날짜를 지키려면 UTC 00:00~14:59 안에 있어야 한다.**
즉 KST 09:00 이후로 잡아야 같은 날이다.

07:31 을 유지하려면 UTC 로는 전날 22:31, 곧 말일이 된다.
말일은 달마다 28~31 로 달라 cron 으로 정확히 못 잡는다.
그래서 **09:31 KST(`31 0 1,15 * *`)** 로 옮겼다.

> **교훈**: 날짜가 걸린 cron(`1,15`, `L`, 요일)은 UTC 변환 뒤
> 날짜가 넘어가는지 반드시 확인한다. 시각만 맞추면 날짜가 틀어진다.
> 요일도 마찬가지다 — 평일 17시 KST 는 UTC 로 `0 8 * * 1-5` 가 맞지만
> 평일 07시 KST 는 `0 22 * * 0-4` 로 **요일까지 당겨야** 한다.

### 화성시 게시판 페이징을 못 찾고 있었다 (2026-09-17 해결)

`collect_hscity.py` 주석에 이렇게 적혀 있었다.

> 페이지 필드 이름은 아직 못 찾았으므로, q_currPage 를 같이 보내보고
> 1페이지와 결과가 같으면 페이지 넘김이 안 되는 것으로 보고 멈춘다

그래서 부서당 10건씩만 쌓였고 누적이 284건이었다. 현안 연표를 만들 표본이 안 됐다.

**원인**: `q_currPage` 는 폼에 있지만 **단독으로는 무시된다.**
`q_cp` 를 함께 보내야 서버가 페이징 요청으로 인식한다.
`q_cp` 는 값과 무관하고 **있기만 하면** 된다.

```
q_currPage=2 단독        → 1페이지
q_cp=2       단독        → 1페이지
q_cp + q_currPage=2      → 2페이지 ★
q_cp=1, q_currPage=2     → 2페이지 (q_cp 값은 무관)
```

**찾은 방법**: 개발자도구 없이 워크플로로 후보를 대입했다.
1차는 파라미터를 하나씩 던져 전부 실패했고,
페이지의 hidden 필드 8개를 통째로 보낸 뒤 하나씩만 바꾸는 2차에서 찾았다.
이 서버는 **폼 전체를 받아야 판단하는 구조**였다.

같이 알아낸 것.

| 항목 | 결과 |
| --- | --- |
| 전체 규모 | 고시 688페이지, 일반공고 953페이지 (약 16,000건) |
| 부서 필터 | 먹는다. 단 **드롭다운에 없는 이름은 오류 없이 0건** |
| 제목 검색 | 안 된다 (`query` 포함 8개 이름 × 4개 타입 전부 실패) |
| 시기 | 50p=2025-11, 100p=2024-12, 150p=2024-04, 200p=2023-08 |

**백필을 부서별에서 전체 훑기로 바꾼 이유**가 두 번째 줄이다.
`WATCH_DEPTS` 의 "트램건설추진단" 은 드롭다운에 없는 이름이었고,
없는 부서와 똑같이 0건이 왔다. 이름이 하나라도 틀리면 그 부서가 통째로 빠진다.
전체를 훑으면 부서명을 몰라도 빠지는 것이 없다.

> **타임아웃 사고** — 처음에 150페이지로 돌렸다가 15분 제한에 걸려 취소됐다.
> 더 나쁜 것은 **출력이 하나도 안 남았다**는 점이다. 파이썬이 표준출력을
> 버퍼에 담고 있다가 통째로 날아갔고, 긁은 데이터도 저장 전이라 사라졌다.
> 그래서 `log()` 로 `flush=True` 를 강제하고 20페이지마다 중간 저장한다.

**조치**: `category in INFO_TRACKS`를 맨 앞 조건으로 두고 차단.

### 도입 문구가 사실과 다른 문장을 박고 있었음 (2026-09-16)

H1 바로 아래에 코드가 자동 삽입하는 문장이 하나 있다. Claude가 쓰는 게 아니다.

```
"최근 지식산업센터 관련 검색 데이터를 살펴보니, {top_keyword}을(를)
 찾아보는 분들이 가장 많았습니다."
```

아젠다 순환에서는 `top_keyword`가 **검색 점수 1위가 아니라 순환으로 고른 현안명**이다.
그대로 두면 "…살펴보니 **트램**을 찾아보는 분들이 가장 많았습니다"가 된다. 거짓이다.

**조치**: `track`에 따라 세 갈래로 분기.

| 트랙 | 문구 |
| --- | --- |
| `council` | 화성특례시의회 회의록을 최근 한 달치 훑어 정리했습니다 |
| `local` | 동탄에서 계속 지켜보고 있는 지역 현안 가운데 **{현안명}** 소식을 정리했습니다 |
| 그 외 | 기존 문구 유지 |

**교훈**: 코드가 본문에 직접 문장을 넣는 지점은 따로 목록을 만들어 관리한다.
프롬프트를 아무리 고쳐도 이런 문장은 안 바뀐다.

### UTC 날짜가 세 파일에 남아 있었음 (2026-09-16)

A2의 "요일 판별 주의"는 `pick_track()`만 고쳤다. 나머지는 그대로였다.

현안 목록을 갱신하는 경로가 아직 수기뿐이다. 설계는 아래까지 확정됐다.

**텔레그램 형식** — 번호대를 나눠 오타를 잡는다.

```
[안건 점검] 10/01

■ 현재 안건 (- 로 보류)
1 A001 트램                 착공준비 · 9/08

■ 뉴스 후보 (+ 로 채택)
11 동탄2 신규 지산 공급 물량 (뉴스 4건)
12 화성 국가산단 전력공급 협약 (뉴스 3건) ※A005와 유사

답장 예: -2 +11 +13
무응답 = 변경 없음

**확정된 설계 6가지**

1. **무응답 기본값이 키워드 발굴과 반대다.** 키워드는 무응답 시 전부 채택이지만,
   안건은 무응답 시 **아무것도 바꾸지 않는다.** 답장을 놓친 날 목록이 흔들리면 안 된다.
2. `-`는 삭제가 아니라 **`상태`를 보류로.** 행을 지우면 진전 이력이 함께 사라진다.
3. 기존 안건은 **1번대**, 뉴스 후보는 **11번대.** `-11` 같은 오타가 조용히 무시되지 않는다.
4. 중복 판정은 키워드 토큰 겹침으로 하되 **자동으로 지우지 않고** `※A005와 유사`만 표시한다.
   자동으로 걸러내면 실제로는 다른 사안인데 사라진다.
5. 답장 처리 시점에 **CSV를 다시 읽고 병합한다.** 07:10 고시 수집이 그 사이 단계·진전일을
   갱신했을 수 있다.
6. 신규 안건은 `추가일` 기준 **30일 스킵 면제**를 받는다 (A9 참조).

# Part E — 업체 데이터베이스

> **정리일** 2026-09-19 · **상태** 1차 구축 완료 · 분기 갱신 체계 가동 중
>
> 블로그 파이프라인과 별개로 도는 프로젝트다. 데이터도 실행 환경도 따로이고,
> 같은 저장소에는 갱신 알림만 얹혀 있다.
> 다만 블로그 소재의 한 축이라 여기 함께 둔다.

## E1. 추진 배경

### 최종 목표

2030년 정년 퇴직 후 **2동탄 지식산업센터 전문 공인중개사 개업**.
개업 시점에 "이 업체는 곧 움직인다"를 판단할 수 있는 근거를 미리 확보하는 것.

### 시작점과 방향 전환

이 프로젝트는 처음에 **협력업체 사업자등록번호 검증**으로 출발했다.
사업자번호로 주소·전화번호·대표자를 알아낼 수 있는지 알아보는 것이 시작이었다.

진행 중 실제 목적이 드러났다. 검증이 아니라 **중개업 잠재고객 명단 확보**였다.
이 전환이 프로젝트 성격을 완전히 바꿨다.

### 중간에 한 번 더 전환한 것 — 가장 중요한 판단

개업까지 4년이 남았다는 점을 다시 따져본 결과, **"잠재고객 리스트 확보"라는
목적 자체를 폐기**했다.

사업체 명단은 빠르게 상한다. 폐업·이전·상호변경·대표교체가 누적되면
4년이면 절반 가까이 못 쓰는 정보가 된다. **2026년에 만든 리스트를 2030년에
들고 영업하면 절반은 헛걸음이다.**

더 중요한 건 지금 만들 이유가 없다는 점이다. 개업 6개월 전에 같은 스크립트를
돌리면 그때의 최신 리스트가 10분 만에 나온다.

**그래서 목적을 이렇게 재정의했다.**

> 지금 만드는 것은 "고객 리스트"가 아니라
> **"리스트를 언제든 뽑아내는 기계 + 축적되는 이동 패턴"** 이다.

리스트는 상하지만 패턴은 상하지 않고, 시간이 지날수록 값어치가 올라간다.
4년간 16개 스냅샷이 쌓이면 어떤 업종이 몇 명 규모에서 움직이는지,
이전 전 평균 몇 년을 머무는지, 동탄 안에서 도는지 기흥으로 빠지는지가 보인다.
**남이 돈 주고 살 수 없는 정보이고, 지금부터 쌓은 사람만 갖는다.**

## E2. 데이터 소스 조사 결과

### 사업자등록번호로 얻을 수 있는 것 — 4계층

| 계층 | 출처 | 얻는 것 | 비용 |
|---|---|---|---|
| 1 | 국세청 오픈API | 사업자 상태(계속/휴업/폐업), 폐업일자, 과세유형 | 무료 |
| 2 | 국민연금·건강보험·공정위·DART·KISCON | 주소, 가입자수, 업종, 연락처, 재무, 면허 | 무료 |
| 3 | 민간 DB (bizno, 캐치, 잡코리아) | 상호·주소·대표자·전화·직원수 | 무료(부정확) |
| 4 | 유료 신용정보 (NICE디앤비, 이크레더블) | 신용등급, 재무제표, 담보·소송 | 유료 |

**핵심 제약:** 국세청은 주소·대표자명을 알려주지 않는다. 이미 아는 값이
맞는지 **검증만** 가능하다.

### 두 개의 샘플로 확인한 것

| | 법인·상장 (제우스) | 개인사업자 |
|---|---|---|
| 웹 검색으로 확보 | 거의 전부 | 전무 |

이 대비가 결론을 냈다. **검색 기반 수동 조회는 실무에 못 쓴다.**
API 기반 자동화가 필요하다.

### 부수적으로 발견한 함정

민간 DB를 **상호명으로 매칭하면 안 된다.** "제우스"로 검색 시 평균연봉이
2,776~3,907만원인 서로 다른 업체 4곳이 나왔고, 그중 하나는 업종이
"과실류 도매업"인 완전히 다른 회사였다. **반드시 사업자등록번호로 매칭.**

## E3. 최종 선택한 데이터 구조

### 본체 — 국민연금 가입 사업장 내역

사업장별로 네 가지가 들어 있다.

- **어디에** — 도로명 또는 지번 주소 (건물번호 없음, 도로명까지)
- **무슨 일** — 업종코드, 업종명
- **몇 명** — 가입자 수, 신규취득·상실 인원
- **언제부터** — 적용일자, 탈퇴일자

가입자 3인 이상 법인, 10인 이상 개인사업장만 공개된다.
1~2인 사업장은 애초에 안 잡힌다.

### 보조 — 한국산업단지공단 전국등록공장현황

회사명·산업단지명·생산품·공장주소. 산업단지명을 붙이는 데 쓴다.
사업자등록번호는 개인정보 식별 가능성 때문에 빠져 있어,
**정규화 상호 + 지역**으로 매칭한다.

### 핵심 설계 — 덮어쓰지 않고 쌓는다

**주소 이전이나 인원 증감은 어느 소스도 알려주지 않는다.**
같은 데이터를 분기마다 스냅샷으로 쌓아야만 나중에 비교로 산출된다.

오늘 받은 파일을 덮어쓰면 그 시점은 영원히 사라진다.
그래서 누적형 DB로 만들었고, **원본 CSV도 계속 보관한다.**

  (드라이브에 직접 쓰면 SQLite 파일이 깨질 수 있어서)

### 상호명 정규화 — 매칭의 핵심

사내 데이터와 공개 데이터의 상호 표기가 제각각이다.

```
(주)제우스 / 제우스(주) / 주식회사 제우스 / ㈜제우스 / 제우스
→ 전부 '제우스'로 통일해 비교
```

매칭 등급 세 단계로 나눠 기록한다.

| 등급 | 조건 |
|---|---|
| 확실 | 사업자번호 앞 6자리 + 정규화 상호 완전 일치 |
| 유력 | 앞 6자리 일치 + 접미사만 다름 (제우스 / 제우스화성공장) |
| 의심 | 상호만 일치, 번호 불일치 (동명 업체 위험) |

8개 테스트에서 7건 연결, 나머지 1건은 소멸 케이스로 정상.

## E6. 확인된 한계

### 건물 단위 특정이 불가능하다

국민연금 공개 데이터는 **도로명까지만 있고 건물번호가 없다.**
개인정보 보호 차원에서 상세주소를 잘라낸 것으로 보인다.

```
경기도 화성시 동탄구 동탄영천로      ← 여기까지
경기도 화성시 동탄구 동탄산단6길
```

같은 도로에 지식산업센터가 여러 개면 구분이 안 된다.

### 대신 도로명 단위 성격 분류는 가능하다

평균 인원이 성격을 잘 드러낸다.

| 도로명 | 사업장 | 평균인원 | 성격 |
|---|---|---|---|
| 동탄첨단산업1로 | 454 | 16.1 | **지식산업센터 밀집(테크노밸리)** |
| 동탄순환대로 | 248 | 17.8 | 혼재 |
| 동탄기흥로 | 383 | 13.1 | 혼재 |
| 동탄대로 | 421 | 8.5 | 상가 위주 |
| 동탄산단6길 | 53 | 90.5 | 제조 공장 |
| 동탄대로9가길 | 21 | 128.8 | 대기업 사옥 |

**동탄첨단산업1로는 동탄테크노밸리와 완전히 일치**한다.
반면 동탄순환대로·동탄기흥로는 2동탄 주요 간선도로라
전체적으로는 산업단지와 무관하다.

→ **지식산업센터 건물별 태깅은 현 데이터로 불가.**
   정밀 매핑은 2029년경 실거래가·경매 데이터로 하는 것이 정확하다.

### 법적 고려

수집한 연락처로 **영업 문자·전화를 돌리는 것은 정보통신망법상
사전 동의가 필요하다.** 명단 보유나 시장 분석·물건 매칭 용도는 문제없다.

블로그로 신뢰를 쌓아 문의가 들어오게 하는 전략과는 오히려 잘 맞는다.

## E7. 현재 운영 체계

### 갱신 주기 — 분기 1회

월 단위는 인원이 한두 명 왔다갔다 하는 노이즈가 많다.
**분기 단위가 실제 변화를 더 선명하게 보여준다.**
2030년까지 16개 스냅샷이 쌓인다.

### 잊지 않게 하는 장치

`jisik-blog-auto` 저장소에 알림 스크립트를 붙였다.

- `scripts/check_bizdb_freshness.py`
- `.github/workflows/bizdb-freshness.yml` (매주 월요일 점검)

C2 의 ⑦(텔레그램 답장 충돌)과 무관하다. 이 알림은 **발송 전용**이라
`getUpdates` 를 부르지 않는다.

**갱신할 게 없으면 아무것도 안 보낸다.** 시점이 다가오면 보내기 시작하고,
2주 넘게 방치되면 `🔴`로 바뀌며 며칠 지연됐는지 알려준다.

블로그 파이프라인과 같은 봇을 쓰되 **발송 전용**이다.
답장을 읽지 않아 초안 승인 봇과 충돌하지 않는다.

### 갱신 절차 (알림에 그대로 포함됨)

1. data.go.kr에서 `국민연금공단_국민연금 가입 사업장 내역` 검색
2. **반드시 '파일데이터' 탭에서** 다운로드 (오픈API 탭 아님)
3. 드라이브 `bizdb` 폴더에 업로드 (**기존 파일 지우지 말 것**)
4. Colab `업체DB.ipynb` → 1·2·3번 셀 실행
5. `다음 분기 자료 추가` 셀 실행
6. `check_bizdb_freshness.py`의 `LAST_UPDATED` 날짜 수정 후 커밋

**다음 갱신: 2026년 10월 말~11월 초**
등록공장현황도 같이 받을 것 (현재 2024-12 기준으로 오래됨)

## E8. 향후 진행 방향 — 2030년까지

### 2026~2027 · 쌓는 기간

**할 일은 분기마다 파일 받아 적재하는 것뿐. 분기당 15분.**

분석은 하지 않는다. 스냅샷이 4~6개는 돼야 뭐가 보인다.
이 기간의 주력은 블로그이고, DB는 콘텐츠 소재로만 쓴다.

### 2027년 초 · 첫 성과 지점

12월 스냅샷이 들어가면 2026년 6월과 비교가 가능해진다.
반년 사이 어떤 업체가 인원이 늘었고 어디로 옮겼는지가 처음 보인다.

반년치라 패턴이라 부르긴 이르지만, **블로그 소재로는 쓸 수 있다.**

### 2028 · 패턴이 보이는 시점

스냅샷 8개. 업종별 이동 주기, 규모 구간별 이전 확률이 나온다.
**"동탄 지산 입주기업 2년 추적"** 같은 시리즈는 아무도 못 쓴다.

### 2029 · 실무 준비

권역별 수요 지도 정리. 실거래가·경매 데이터와 결합.
지식산업센터 건물 단위 정밀 매핑도 이 시점에.

### 2030 · 리스트 생성

개업 6개월 전 최신 스냅샷으로 실제 명단 추출.
이때 유료 API로 연락처 보강 (500건 기준 5만~8만원).
**그 시점 기준 최신이라 바로 쓸 수 있다.**

### 시간 배분 권고

향후 2년간 **블로그·실거래가에 80%, DB에 5%**, 나머지는 경매·계산기.

DB는 손이 많이 가는 것처럼 느껴지지만 실제로는 분기당 15분이다.
**손이 많이 갔던 건 구축 단계였고 그건 끝났다.**
이제부터는 유지만 하면서 시간이 일하게 두면 된다.

## E9. 활용 방안

### 개업 전까지 — 블로그 콘텐츠

이게 즉시 현금화되는 유일한 가치다.
Part A 의 어느 트랙에 넣어도 된다. 지산 본류에서는 판단 재료로,
지역 개발에서는 배경 숫자로 쓴다.

동탄권 4,030개 사업장, 가입자 86,818명, 10~29명 구간 1,081개,
반도체 소자 제조업 215개에 소프트웨어 109개.
**이런 자체 데이터를 가진 블로그는 동탄에 없다.**

실거래가 데이터([[B1]])가 공급 쪽이라면 이 DB는 수요 쪽이다.
둘을 합치면 **"동탄 지산 공실이 왜 이 정도인가"를 양쪽 숫자로
설명할 수 있는 몇 안 되는 사람**이 된다.
그게 개업 시점의 신뢰 자산이 된다.

### 분기 비교에서 나오는 것

| 신호 | 중개업 관점 의미 |
|---|---|
| **인원 급증 업체** | 곧 넓은 곳을 찾을 후보 — 가장 값어치 있는 신호 |
| **주소 변경 업체** | 실제 이동 흐름, 어디서 어디로 가는지 |
| 신규 등장 | 새로 들어온 업체 |
| 사라짐 | 폐업 또는 이탈 |

### 개업 후

- 업종·규모별로 분류된 잠재 고객 명단
- 이동 패턴 기반의 타이밍 판단
- 상가 중개용 별도 세그먼트 (의원·학원·음식점 등)
- 물건 매칭 시 "이 건물에 어떤 업종이 모여 있는가" 근거

## E10. 해결한 문제들 (재발 시 참고)

| 증상 | 원인·해결 |
|---|---|
| 파일 `못 찾음` | 드라이브 경유 시 한글 자모 분리. NFC 정규화 + 파일크기 순 배정 |
| `IsADirectoryError` | 파일 경로가 빈 문자열. 위와 동일 원인 |
| `NameError: DB is not defined` | Colab 세션 끊김. 1번 셀 재실행 |
| 창 닫혀 작업 유실 | 단계별로 셀 분리, 각각 드라이브 저장하도록 변경 |
| 주소 일부 누락 | 도로명이 비면 지번주소를 쓰도록 행별 대체 로직 |
| 탈퇴 사업장 혼입 | 가입상태코드로 등록(1)만 집계 |
| 체크포인트 덮어쓰기 | 기본키를 (bizno, kind) 복합키로 변경 |
| 단지 색상 중복 | 해시 배정 → 사용 순서 배정으로 변경 |
| API 503 오류 | 국세청 서버 장애. 키·코드 문제 아님. 시간 두고 재시도 |
